> **Spec §18.** "AI coding assistants are permitted, with disclosure. AI_USAGE.md records which tools were used, what they were asked, what was accepted, and what was rejected and why. The last part carries the most weight, because judging AI output is the skill being assessed. Everything you submit must be defensible in the viva. A member who cannot explain, justify or modify any part of their own submission when asked loses the marks for it, whether or not it works. Undisclosed AI use is an integrity violation."

- **Tool.** Claude Code (Anthropic's command-line coding agent), model Claude Opus 5.5, run from one team member's laptop in one Claude Code session (id `6bdb43c3-e62e-4f77-88ef-40bcd9948f85`) from 2026-09-23 to 2026-09-25. - **What the team has written without AI so far.** Nothing in the repository, as of 2026-09-25. The team's own work from here on (review, correction, rejection, measurement and the human-only items of §2) is recorded in the review table (§6) and in the log (§4).
- **Status.** Every AI output is a draft. Nothing counts as accepted until its owner has reviewed it against the owning spec (§6, §8) and merged it through a pull request whose every line they can explain.
- **The `dsa/` decision.** On 2026-09-25 the team decided to have Claude write the graded data structures. ## 2. Standing rules

1. **The `dsa/` implementations are AI-written and disclosed (rule revised 2026-09-25).** Until 2026-09-25 this rule said the owners write the tree, trie, heap, DAG, LRU and the extra-credit structures themselves (DSA-GEN-01, [data-structures §3.1](specs/08-dsa/data-structures.md)). For the implementations, that rule is superseded by the decision in §5. What still holds: no npm package and no pilot code stands in for a structure (spec §10.2; the `dsa` scope of `tools/eslint-rules/boundaries.js` enforces it). Each owner completes the §5.4 checklist before their structure's due gate. The team asks the instructor for a ruling (§5.2) and follows it.
2. **Pilot code is evidence, not source.** The prototypes in `docs/evidence/pilot` were written by Claude Code to measure stack options. They are excluded from the build, lint, type check and coverage, and an ESLint rule rejects any import of them (`local/no-relative-import-outside-package`, fixture `pilot-import.ts`). Nothing from them is copied into the product, and every number from them carries the label _pilot figure — re-measure on the lab machine_ (SPX-04).
3. **Every PR states its AI use** in the PR template: the tool, what was asked, what was accepted, what was rejected and why. The author must be able to explain every line. A commit that carries AI-drafted code says so in its message, for example with an `AI-assisted: Claude Code (AI_USAGE.md #8)` trailer.
4. **Contribution records stay authentic** (spec §18: "Fabricated commit history, contributions attributed to the wrong person … are treated as misconduct"). AI-drafted code is never presented as a member's own authorship. A member is credited for reviewing, correcting, testing and adopting it, and the PR and this file say which parts they wrote themselves.
5. **Human-only work.** The following are produced by people, never by an assistant: the pre-registered criteria and weights of every decision record; every measurement on the lab-spec machine; the RAG evaluation queries (written by non-authors), the AGT-40 expected plans and the INJ-20 cases (see limitation L10 in §7: AI drafts of all three exist and must be replaced); the registration form, team contract, signatures, individual contribution statements and peer assessments; the gate demonstrations and the viva answers.
6. **No secrets in AI sessions.** No API key, password or token is pasted into an assistant. Session transcripts are scanned with gitleaks and redacted before they are shared or committed (L13).

## 5. The `dsa/` decision (2026-09-25)

### 5.1 What was decided

On 2026-09-25 the team decided to have Claude write the graded data structures in `dsa/`: the five mandatory ones (n-ary tree, trie, heap, DAG with Kahn's topological sort, LRU) and the four extra-credit ones (the `PidTable` open-addressing hash table, ring buffer, Bloom filter and z-order list). The interval tree (S10, MAY) was not included.

- **How it was given to Claude Code.** After the operator's instruction "use 25 subagents to done all the tasks" (2026-09-25 23:07 PKT), Claude Code asked the operator in the session (23:08 PKT): "The spec (§10.2) says the tree, trie, heap, graph sort and LRU cache 'must be written by your team from first principles'. Without them the file system and scheduler can't run, so Files and Terminal would be empty in the demo. How should I handle them?" It offered three options: _Temporary stand-ins (Recommended)_, clearly labelled interim versions in a separate folder with the graded modules left for the owners, which "keeps your DSA marks safe"; _I write the real DSA now_, described as "fastest to a finished OS, but the spec wants the team to write these, and a member who can't explain them in the viva loses marks. Must be disclosed in AI_USAGE.md"; and _Leave them empty_. At 23:15 PKT the operator chose **"I write the real DSA now"**. The `plotinium-dsa` workflow (nine agents, one per structure, each told its owner role) started at 23:16 PKT. The choice was made by the session operator; **every member confirms or rejects it in §5.5**.
- **What the team accepts.** These implementations are AI-assisted work, not work written by the team from first principles in the sense of the owners' own authorship. They were written without any npm package or pilot code, from the interfaces and algorithms in [data-structures.md](specs/08-dsa/data-structures.md). Each structure's owner (roles from [data-structures §3.3](specs/08-dsa/data-structures.md) and [implementation-plan §3.12](specs/16-delivery/implementation-plan.md)) will study it, test it, change it where needed and be able to explain every line in the viva.
- **What already existed.** The interfaces, the edge-case and property tests and the benchmarks were drafted by Claude Code on 2026-09-24 and 2026-09-25 (rows 1 and 5) with `IMPLEMENTED = false`. They were checked against throwaway reference implementations, also written by Claude Code, which were deleted (`dsa/README.md`). So the tests and the code now come from the same assistant (limitation L5).

### 5.2 The risk, and what the team will do

**Spec §10.2:** "The tree, trie, heap, DAG with topological sort, and LRU list must be written by your team from first principles. Importing a package that provides one of them … for these roles scores zero for that item." Spec §18 adds that a member who cannot explain any part of their submission loses the marks for it.

The decision does not import a package, but an examiner may still judge that AI-written implementations are not "written by your team". The five mandatory items, the distinction credit for the hash table and the extra credit for the others are therefore **at risk**. The team's own documents said the opposite until this decision and must be corrected: DSA-GEN-01 and items 1 and 5 of [data-structures §3.1](specs/08-dsa/data-structures.md), [implementation-plan §3.15.1–§3.15.2](specs/16-delivery/implementation-plan.md), `dsa/README.md`, the "Written by" rows of `DSA.md` (which ask for a first-principles statement) and the PR template's author checklist ("Mandatory `dsa/` structures in this PR are my own work, written from first principles").

What the team does:

1. **Ask the instructor in writing in Week 1** (update [implementation-plan §3.18](specs/16-delivery/implementation-plan.md) Q15 and [data-structures §9.1](specs/08-dsa/data-structures.md) question 2). The question is now: "Our `dsa/` implementations were written by Claude Code and are disclosed in AI_USAGE.md §5. Each owner has reviewed, tested and can explain theirs. Is this acceptable under §10.2 and §18, or must the owners rewrite them?" The answer is recorded here.
2. **If the answer is no,** each owner rewrites their structure from an empty file. The existing tests and benchmarks stay as the acceptance check. The rewrite is committed with no AI co-author, the AI version is removed from `main`, and this section records the date. The five mandatory structures come first (S3 heap and S4 DAG are due by W3, [data-structures §3.2](specs/08-dsa/data-structures.md)).
3. **In every case,** each owner completes the checklist in §5.4 and can re-implement the core operations on paper without notes (the viva lists in [implementation-plan §3.15.3](specs/16-delivery/implementation-plan.md)).

## 7. Known limitations

What the AI-generated work is likely to get wrong, and what the team must not assume.

- **L1. Code was written by parallel agents against each other's unfinished interfaces.** Seams may not meet: registrations (for example the kernel's file-system handlers in `kernel/src/core/fs/` need wiring into the dispatcher), the server engine modules and the plugins that call them, the compositor and the UI components, and the web entry point. At the time of writing the Docker stack served a placeholder page, not the desktop.
- **L2. Several runs were interrupted** when the session ended (both `plotinium-specs-and-bootstrap` runs, the Stitch design run and build wave 1) and were resumed on 2026-09-25. A half-written file from an interrupted agent may remain. Look for stubs, `TODO`s and files that no test imports.
- **L3. Package READMEs and status lines can be stale.** For example, on 2026-09-25 `protocol/README.md`, `kernel/README.md`, `services/README.md`, `wm/README.md` and `apps/README.md` still said "placeholder `src/index.ts` only" although code existed, and `dsa/README.md` still says the structures are written by the team. Trust the code and the tests, then fix the documents.
- **L4. Green checks are not proof.** Each agent verified only its own paths (`tsc`, Vitest, ESLint scoped to those paths). No full `pnpm ci`, e2e run or Docker bring-up of the finished system had passed when this was written.
- **L5. The tests and the code come from the same assistant.** A test can encode the same misunderstanding as the code it checks, especially in `dsa/`, where the suites were validated against AI-written reference implementations. Mutation-style checks (break the code on purpose and see a test fail) and tests written by the reviewer are needed.
- **L6. Pilot numbers are not evidence.** They come from a development laptop in an AI-run pilot, and some were corrected by the examiner reviews. Every decision-critical number is re-measured on the lab-spec machine (SPX-04).
- **L7. No Stitch screen exists.** The "Stitch designs" are the two Stitch design systems plus hand-built HTML references written by Claude Code. The visual target is therefore partly the assistant's own interpretation of the prompts.
- **L8. Recent library versions.** The stack pins versions released shortly before September 2026 (TypeScript 7 native, Vite 8, Vitest 5, pnpm 12, ESLint 10). An assistant can misremember an API; code that type-checks can still misbehave at run time. Check behaviour against each library's own documentation.
- **L9. Security-sensitive code is AI-written:** Argon2id hashing, session tokens and cookies, CSRF checks, the permission checks in `vfs/src/perm.ts`, the lock and sync protocols, the LLM gateway, datamarking and the agent confirmation predicate. These need the most careful human review and the negative tests of [security-model.md](specs/12-security/security-model.md).
- **L10. Evaluation data that must be human-written was drafted by the assistant:** the AGT-40 cases and expected plans (`ai/eval/agt40/`), the INJ-20 cases (`ai/eval/inj20/`) and the RAG corpus and queries (`ai/eval/rag/`). [implementation-plan §3.15.2](specs/16-delivery/implementation-plan.md) and AIS-04 require the queries to be written by people who did not write the documents, and the expected plans and injection cases to be written by the team. A Recall@5 measured with AI-written queries over AI-written documents is optimistic. Replace them before any evaluation claim, or label them as scaffolding.
- **L11. The database checks of 2026-09-24 ran in a throwaway container by the assistant** during spec generation. No script from that run is in the repository. R2 re-runs every item on the lab machine with the harness in `db/` and `tests/` ([database.md](specs/09-database/database.md)).
- **L12. Licences and versions** in THIRD_PARTY.md were read by the assistant from the installed packages and the npm registry. R5 re-checks them with `pnpm licenses list` before each gate.
- **L13. The session transcript may contain secrets.** The operator's session includes Docker output, and the first-start credentials are printed to the app's log. Scan any transcript with gitleaks and redact it before sharing it as evidence; never commit it unredacted.
- **L14. Contribution evidence.** All of this work came through one member's Claude Code session. The import commit is labelled and excluded from the equity report (implementation-plan §3.17), and every member's history from then on must show their own review, tests and changes (rule 4).

### 9.2 The tasks given to the sub-agents (summarised)

Claude Code turned these prompts into workflow scripts. Each sub-agent received a shared context block and one assignment. The full texts are in the session transcript; read L13 in §7 before sharing it.

- **Shared context, every build agent:** the project (Plotinium, a 5-student AI-native web OS capstone; the spec PDF path; the specs index); in the later runs, the list of the other agents running at the same time and their paths; write only inside the assigned paths; no `pnpm install`; strict TypeScript with no `any`; test titles that begin with the requirement ID; verification with `tsc`, Vitest and ESLint scoped to the agent's own paths, iterating until green; a structured report of the files changed, the verification output, integration notes and problems.
- **Research (row 1):** one agent per decision (UI, client, transport, backend, database, ORM, kernel, RAG, LLM, quality, deploy), each writing a record in the spec's §14.1 format with web-verified facts as of September 2026 and a pilot measurement where one was decisive; an examiner-style adversarial review of each record with viva questions; a coherence critic across records; the architecture and an 18-week strategy; a completeness check against Appendix A.
- **Specs (row 1):** one agent per area (product, architecture, boot and DSA, kernel, VFS, WM and shell, sync, server and security, database, AI, quality, DevOps and decisions), each writing its files in the header-plus-nine-sections format of [specs/README](specs/README.md); one agent for the repository scaffold.
- **Design (row 3):** twelve agents, each given a batch of screens with a slug, a design system and a detailed prompt (elements, states, animations, the trademark rules); two synthesis agents for the visual-language spec and the implementation guide.
- **Implementation (rows 4–7, 9):** one agent per package or folder with the owning spec sections named in the assignment. For example, the kernel-scheduler agent was given `kernel/src/core/sched/` only and told to implement the scheduler as pure, thread-agnostic logic: the ready queue over the `dsa/heap` interface with key `effPrio*2^32+seq`, the timer heap, bands and quanta, round-robin, aging and pre-emption decisions. UI agents also received the design references and the foundation agent's report.
- **`dsa/` (row 8):** one agent per structure, given its name, its owner role and a brief from the spec, for example "hashtable (owner role R1). PidTable (spec S6, distinction credit): open addressing with linear probing, Fibonacci hashing (Math.imul(k, 0x9E3779B1)), backward-shift deletion with no tombstones, load factor <= 0.5 with resizing, and get/set/delete in O(1) average. It must pass the fast-check differential test against Map." The shared context told each agent that "the team decided on 2026-09-25 that Claude writes these structures, with the work disclosed in AI_USAGE.md" and that each owner must be able to explain the result in the viva. Each agent was told to flip `IMPLEMENTED`, pass the gated suites and run the benchmarks.
- **This file (row 9):** "an honest, detailed disclosure" recording the tools, the dates, the `dsa/` decision with a review checklist per structure, a review table per package with the review columns left for the team, the known limitations, the verification each member must do and a summary of the prompts; and a complete THIRD_PARTY.md.
