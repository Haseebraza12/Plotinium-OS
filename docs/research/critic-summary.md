VERDICT: I checked the stack and strategy against the whole spec (/home/haseeb-raza/Desktop/Plotinium OS/CapstoneProject-AI-Native WebOS-Fall2026.pdf), including the Appendix A checklist, the milestones on pp. 42-43, repo and testing on pp. 45-47, boot, OS primitives, the database and AI. The stack itself is sound: PostgreSQL + pgvector, Kysely + dbmate, a worker kernel, IndexedDB + OPFS, raw WSS, a server-side LLM gateway, and hand-written DSA modules under dsa/. Nearly every requirement ID has a home and a named test.

Several problems would still fail a must, a numeric target or a gate:
1. **AI-native properties (s3.2).** The strategy argues two subsystems together cover all four properties, but the spec requires all four for each subsystem. The table leaves gaps for RAG and pre-fetch.
2. **Frame-time gate.** The stack sets it at refresh + 1 ms, which is 17.67 ms at 60 Hz and fails the ≤ 16.7 ms target.
3. **RAG-03.** Other users' chunks with stale local permissions can leak in search results.
4. **Resume feed.** It is keyed by the acting user, so other users' changes are missed and the tree does not converge.
5. **Client storage model.** Per-uid IndexedDB contradicts both the boot DAG and the P2 multi-user demo.
6. **Executors.** The placement rules cannot be satisfied under the executor clamp on 4-thread machines.
7. **Memory.** The MEM-06 guard reacts too late, and MEM-04/05 remote swap would hold no data on a lab PC with plenty of quota.
8. **Scheduler bound.** The PROC-04 bound is under-stated, and the test asserts against a different number than the one declared.

Missing mandatory homes:
- the DAG for application start-up dependencies;
- trie coverage of flags and history;
- the index list for the benchmark queries (Q1-Q5);
- CHECK constraints on type and mode (DB-04);
- inode IDs that match between client mkfs and the server seed;
- an agent observation loop with read-only tools, which puts AGT-07 at risk;
- OFF-05 in the gate and demo scripts.

Integrity and security problems:
- a production root password in a public README;
- default database credentials committed in compose.yaml;
- cassette recordings that may capture the API key header;
- AI-written pilot DSA code being copied into the repo, with the AI-assisted stack analysis undisclosed.

Schedule: Weeks 1-3 cannot hold the spike catalogue. Phase 3 is overloaded and builds the sync client before the sync server. R4 carries all AI work plus the shell, coreutils and auth.

I checked the Claude API claims against the claude-api skill reference. It confirms Opus 5.5 pricing, that sampling parameters and forced tool_choice return a 400, and that effort defaults to medium. The temperature-0 rule therefore still needs instructor sign-off, or a model that accepts temperature (claude-sonnet-4-6) as a fallback.

None of this needs a different stack. It needs these specific design fixes, re-timed phases and hygiene changes before the Week-4 defence.

- DEMO_UPSTREAM_TOKEN is 'entered at login' in a browser. :: s18: 'API keys, database credentials and tokens do not belong in the repository.' Anyone who reads the README can su to root on the public deployment. From there they can read every user's files (root bypasses rwx), chown, inject faults into other users' operations and spend the LLM budget. => Give examiners production root and examiner credentials on paper at the defence, and rotate them afterwards. - The frame-time gate is 'refresh interval + 1 ms', measured as rAF deltas. :: At 60 Hz that allows 17.67 ms, which fails the spec's p95 ≤ 16.7 ms (PROC-05, WM-03, Appendix A). rAF-delta jitter also puts p95 at about 16.7-17 ms even when no frame is dropped, so the gate is flaky in both directions. The strategy's gate scripts say 16.7 ms, which contradicts the stack. => Set the hard gate at p95 ≤ 16.7 ms. Measure frame time as each frame's duration from a Chrome trace (or as main-thread work per frame from LoAF and Event Timing), not as raw rAF deltas. Document the method in TESTING.md, record the display refresh rate, and agree the method with the instructor before Phase 2.
- Semantic search can leak files through stale client-side permissions (RAG-03). The client index holds chunk text for other users' files pulled from pgvector. The readable set is computed from the local tree, which can be stale: the user was offline, is not watching /home/alice, or the actor-keyed feed missed the chmod. :: Figure 12.1 and RAG-03 require current permissions at query time and zero leaks. A test where alice runs chmod 600 and bob searches right away would show her snippet. => Online, confirm every result from an inode the querying uid does not own on the server before showing it: send the candidate inos to POST /api/search/verify, which re-checks rwx and x on every ancestor in one statement. For foreign-owned chunks, store vectors only and fetch the snippet through the server. Offline, suppress foreign-owned results. Add chmod-while-offline and chmod-while-not-watching cases to the rag-leak suite.
- The change feed and resume are keyed by the actor's uid ('op_log WHERE uid AND srv_seq > since'). :: Alice's resume never includes bob's changes to /home/shared, or to any other file her device mirrors. Re-validating shared directories by readdir versions has no defined scope. This breaks VFS-10 and the s7.3 check that 'the server state converges with no lost operations'. => Write one feed row per affected owner, feed(owner_uid, owner_seq, op_id), inside the transaction under the L1 locks of each affected owner. The client resumes each owner it mirrors (itself plus the owners of shared directories it holds). Add a test: bob edits /home/shared while alice is offline; alice reconnects; tree checksums are equal.
- The stack's per-uid IndexedDB contradicts both the boot DAG and the P2 gate. :: Storage and vfs mount at L1-L2, before login at L3, so the VFS database cannot be chosen per uid. The P2 gate's 'as bob, cat /home/alice/notes.md → EACCES' needs alice's inodes in bob's local tree; with per-uid databases the result would be ENOENT. The server vfsTxn only arrives in W9. => Keep one VFS database per device, with the kernel enforcing rwx. Only verifiers, telemetry, private index text and swap are per uid. State in SECURITY.md that data at rest in the browser profile is readable by anyone who controls that OS account, as on UNIX with physical access.
- The executor placement rules cannot be met under the executor-count clamp. :: On a 4-thread lab PC with ai.embed active, clamp(4-2-1, 1, 6) gives 1 executor. The rules also require separate executors per uid, one for ai.agent, and one for any process that overruns twice. The agent demo (AGT-09) and a root shell would then have nowhere to run. => Separate isolation from concurrency. Allow up to about 8 isolation executors (idle ones cost no CPU), and cap concurrently RUNNING slices with a run-token semaphore of size clamp(...). Test placement with hwc forced to 4.
- The MEM-06 budget guard is reactive and too slow. Accounting is updated only at yield points and page boundaries, and the guard acts after 750 ms above budget. One blkio worker doing write, flush, read-back and verify takes about 15-58 ms per 5 MB. :: Reclaiming about 256 MB from a 512 MB memhog takes roughly 1-3 s. That breaks 'accounted memory never exceeds the budget for more than 1 s', which is live in the demo. => Make admission reservation-based. mem.alloc, mem.declare and page-in block (BLOCKED on mem) until reclaim has freed space, so accounted memory never exceeds the budget. memhog must allocate through mem.alloc. Start reclaim at the 85% mark. Pipeline blkio: hash the buffer once and verify the read-back asynchronously. Log 'max ms over budget' in the test.
- The declared PROC-04 starvation bound is under-stated. :: The proof leaves out the aging-tick phase (effPrio drops only on ticks, which adds up to T_age). The strategy declares 10.0 s but asserts ≤ 10.5 s, and the checklist line is '≤ declared bound'. => Declare W ≤ (p+1)·T_age + ⌈(N−1)/E⌉·(Q+δ) + H_kill with H_kill = 400 ms, parameterised by the measured E, and assert against exactly that value.
