Part I

Why This Project Exists
Before writing any code, a team must understand what it is building and why. This part explains why web
operating systems matter now and what separates a real operating system from an imitation of one. It also
explains why artificial intelligence must be a foundation of the system rather than a feature placed on top of it.


Section 1

Executive Summary
Your team will design and build a complete Web-Based Operating System (WebOS) that runs natively
inside a modern browser. It must boot through a genuine initialisation sequence and present a
multitasking desktop. It must manage a hierarchical UNIX-like file system, schedule background
processes on Web Workers, page idle application state out of memory, and persist everything with
ACID guarantees. Most importantly, it must treat artificial intelligence as a subsystem of the operating
system, not an application running on top of it.

The project is deliberately cross-disciplinary. Operating Systems, Data Structures & Algorithms,
Database Systems and Artificial Intelligence stop being separate courses and become parts of one
working system. Each concept you have studied has a mandatory place in this codebase:

   the process control block is a hash map;
   the scheduler is a heap;
   the directory hierarchy is a tree;
   the startup order is a topological sort of a dependency graph;
   a recursive delete is a database transaction;
   semantic search is cosine similarity between embeddings of your own files.

The project reproduces real systems-engineering constraints. The browser gives you one main thread
and a storage quota that it is allowed to evict. It limits memory and will kill your tab if you exceed it,
and the network can disappear at any moment. Your OS must stay fast within these limits, recover
from failure and remain useful offline. Those are exactly the areas where the industry systems you
will study, Puter and daedalOS, fall short.


  The brief in one sentence
  Build an operating system, not a website that looks like one, in which intelligence is a system
  service.

1.2 What success looks like
On Demo Day, an examiner who has never seen your system clones your repository and starts it. They
boot it with the network disconnected, run a CPU-heavy job while dragging windows, and open more
applications than memory can hold. They then pull the plug on a recursive delete halfway through
and ask your OS, in plain language, to reorganise their files. A successful system keeps its frame rate,
pages memory out and back in without losing a byte, and rolls back the failed delete with no
orphaned directories. It also shows a plan and asks for confirmation before it touches anything. Each
of those behaviours is specified precisely in Part III and listed as a checklist in Appendix A.


Section 2
The Case for a Web Operating System

2.1 The browser has quietly become the computer
For many people, most of the time, the operating system is now simply the thing that starts a browser.
Email, documents, spreadsheets, design tools, code editors, video calls and a large share of enterprise
software run as web applications. ChromeOS turned this into a product: a thin operating system
whose main application is the browser.

Meanwhile, the browser has grown into a genuine runtime platform. It now offers:

   background threads (Web Workers);
   near-native computation (WebAssembly);
   GPU computation (WebGPU);
   a transactional database (IndexedDB) and a fast private file system (the Origin Private File System);
   offline execution (Service Workers);
   two-way networking (WebSockets and WebRTC).




Lahore Garrison University — Department of Computer Science                                                Page 7 of 55
AI-Native Web-Based Operating System — Capstone Project Specification                                           Fall 2026


A platform with threads, storage, a file system, networking and a security sandbox has the raw
materials of an operating system. What it lacks is organisation: a process model, a scheduler, a
memory manager, a file hierarchy with permissions, a window manager and a coherent notion of
users. Providing that organisation is exactly what an operating system does, and it is what your team
will build.


2.2 What a Web Operating System is, and what it is not
A Web Operating System is a software layer that implements classic operating-system abstractions on
top of the browser runtime: processes, files, users, permissions, windows and services. Applications
reach these abstractions through one uniform interface. A WebOS is not a website styled to look like a
desktop. The difference is the same as the difference between an operating system and a screenshot

Section 3
Artificial Intelligence as an Operating-System
Foundation

3.1 From application to primitive
Operating systems have a long history of absorbing capabilities that started as applications.
Networking was once an add-on, and TCP/IP now ships in every kernel. Full-text search was once a
separate program, and file indexing is now an OS service that any application can query. Each time,
the capability moved into the OS for two reasons. It needed privileged, system-wide access to every
file, process and event. And every application benefited from sharing one trustworthy
implementation.

Artificial intelligence is making the same move. Major desktop and mobile platforms now ship
language models as system services rather than stand-alone apps, and browsers have begun to offer
on-device models to web pages. The reason is structural: a model is only as useful as the context it can
see and the actions it can take, and the operating system is where both live.

That is why this specification forbids a cosmetic chatbot. A chat panel that sees only the text you
paste into it, and replies only with text, is an application. An AI subsystem that is part of the
operating system does five things:

   it is notified when files change;
   it indexes them as a background process;
   it answers questions by searching the file system by meaning;
   it turns intent into verified system calls;
   it tells the scheduler what the user is about to need.

3.4 The AI trust boundary
An AI that can act on a file system can also destroy one. The rigour that protects the kernel from
applications must also protect the system from the model. The model is an untrusted user-space
process: it proposes, and the kernel decides. Every AI subsystem you build must respect these
principles:

   Least privilege. The agent runs with the invoking user's identity, never as root, and cannot raise its
   own privileges.
   Plan before acting. Every multi-step action first produces a plan the user can inspect, and a dry
   run that lists exactly which files it will affect.

Lahore Garrison University — Department of Computer Science                                                  Page 11 of 55
AI-Native Web-Based Operating System — Capstone Project Specification                              Fall 2026


   Confirmation. Destructive or irreversible operations need explicit user confirmation.
   Atomicity. A confirmed plan runs as one transaction or not at all. A failure rolls everything back.
   Content is data, never instruction. File contents and file names in the model's context may
   contain prompt-injection attacks. They must never be able to trigger a tool call on their own
   authority.
   Auditability. Every AI-initiated system call is logged with its prompt, plan, user and outcome.
   Graceful absence. When the model is unavailable (offline, rate-limited or failing), the OS keeps
   working and AI features degrade with a clear message.


  The litmus test
  Remove your AI module and rebuild. If only a sidebar disappears, your AI is cosmetic and will be
  graded as such.

  If the scheduler loses its pre-fetch hints, the shell loses natural-language execution and the file
  system loses semantic search, while everything else keeps working, then your AI is foundational and
  correctly isolated. That is the target.

Section 6
The Boot Screen and Boot Sequence

6.1 Why your OS must boot
When a physical computer is switched on, several stages run in order:

1. firmware performs a power-on self-test (POST);
2. a bootloader selects and loads a kernel;
3. the kernel initialises its core data structures;
4. an init system such as systemd starts services in dependency order until the login screen appears.

Each stage exists because something must be ready before something else can run.

Your WebOS needs a boot sequence for the same reason. Before the desktop can appear, several things
must happen in order:

   the kernel creates the process table and starts the scheduler;
   storage is opened, and the file system is mounted and checked;
   the user is authenticated;
   background services (synchronisation, locking, AI indexing and prediction) start in an order that
   respects their dependencies.

The boot screen is the visible face of this process. It is mandatory, and it must tell the truth: every
movement of the progress indicator must correspond to real work finishing.


  Not acceptable
  A progress bar driven by setTimeout or setInterval, a fixed-length animation, or a splash screen that
  hides a desktop that has already loaded. A boot screen that pretends to load is graded as absent.


6.2 What the boot screen looks like
The visual design of your boot screen is yours to choose: minimal, retro BIOS, cinematic, or
something new. What is fixed is the information it shows and the honesty of its progress.

Section 8

Reference Architecture
The architecture below is a reference, not a prescription. You may restructure it, merge or split
components, or choose different technologies. However, your architecture must keep three
boundaries:

1. Applications reach OS resources only through the system-call interface. No application,
   including built-in ones, touches storage, the process table or another application's windows
   directly.
2. The main thread only renders and dispatches. Computation runs on workers. The kernel's own
   work on the main thread is small and bounded.
3. The client can work alone, and the server is the authority on shared state. The client runs offline
   from local state. The backend is authoritative for multi-user data, locks and quotas.

The scheduler
   Ready queue. A binary min-heap that you implement. Its key is (effective priority, arrival sequence
   number). The sequence number gives FIFO order within a priority level, which produces round-
   robin within each priority.
   Aging. A process that waits for longer than a set interval has its effective priority improved step by
   step. No runnable process starves, and you must state and prove the bound.
   Time slices. Long-running work is written as resumable steps (generators, chunked loops or
   explicit state machines). A worker runs one quantum of steps, reports back, and the scheduler re-
   queues the process.
   Pre-emptive and non-pre-emptive classes. Interactive and foreground processes pre-empt
   background ones at the next slice boundary. Non-pre-emptive tasks, such as a transaction commit,
   run to completion. A process that exceeds its hard limit is forcibly terminated with
   worker.terminate().

   Multi-core dispatch. The worker pool is sized from navigator.hardwareConcurrency, and the
   scheduler maps runnable processes onto free workers.
   Main-thread budget. The kernel's bookkeeping must stay small enough that the interface holds 60
   FPS, which is a frame budget of 16.7 ms shared with rendering.


  Engineering reality: pre-emption in a browser
  A running JavaScript function cannot be interrupted from outside. You therefore implement pre-
  emption at two levels. Cooperative time-slicing at yield points handles the normal case. Forced
  termination handles runaway processes. Explaining this trade-off clearly, and what it costs a process
  that is terminated mid-slice, is part of your defence.

9.2 Virtual memory and paging
Your OS is responsible for the memory of every application it runs. Each process has in-memory
state: documents, canvases, editor buffers, emulator state and caches. When the total resident state
exceeds the system's memory budget, the memory manager must reclaim memory in three steps:

1. serialise the least recently used inactive state;
2. write it to swap;
3. release it from memory.

When the process is needed again, the state must be paged back in without the user having to do
anything.

Memory accounting
Browsers do not report exact memory use per object, so your team must define and document an
accounting model. A typical model counts:

   the serialised size of each process's state;
   the declared size of its large assets (blobs, image bitmaps, WebAssembly memory).

Check your model against real measurements, for example the browser task manager or
performance.measureUserAgentSpecificMemory() where it is available (it requires cross-origin
isolation), and report the error.

Pages, the page table and LRU replacement
Each process's state is divided into pages, either fixed-size chunks of serialised state or logical units
such as one document. A per-process page table maps each page to its location (RESIDENT,
LOCAL_SWAP or REMOTE_SWAP), with a dirty bit, a last-access time, a size and a checksum.
Replacement uses a global LRU list, built from a hash map and a doubly linked list so that touching a
page and evicting a page are both O(1). The focused process and pinned system processes are never
evicted.

   Two-tier swap. Tier 1 is local swap in IndexedDB or OPFS: fast, but limited by quota. Tier 2 is

Inodes
Each inode stores the following fields:

   ino: inode number;
   type: file, directory or symlink;
   mode: nine permission bits plus the sticky bit;
   uid and gid: owner and group;
   size;
   nlink: link count;
   atime, mtime and ctime: access, modification and change times;
   blob: reference to the content, for example a content hash;
   target: the target path, for symlinks;
   version: a counter used for optimistic concurrency control.

Path resolution
1. Start at / for an absolute path, or at the process's working directory for a relative one. Split the
    path into components and ignore empty ones, so // is treated as /.
2. For each component, require execute (search) permission on the current directory. . stays in
    place, and .. moves to the parent (at / it stays at /).
3. Look up the child in the directory's hash map. If it is missing, return ENOENT. If a later component
    follows and the child is not a directory, return ENOTDIR.
4. If the child is a symlink, and it is not the last component or the call follows links, resolve its target.
   Relative targets resolve against the link's own directory. Count the hops and return ELOOP after 40.
5. Return the final inode. Operations that must not follow the last link (lstat, unlink, readlink) stop
   one step early.

Permissions, links and quotas
   Permissions. Read, write and execute for owner, group and others. On directories, r lists entries, w
   creates and removes entries, and x allows traversal. Root (uid 0) bypasses read and write checks.
   chmod accepts octal and symbolic modes, chown is root-only, and the default umask is 022. The
   sticky bit on /tmp means only a file's owner can delete it.
   Soft links. ln -s stores a path. A link may point to nothing (a dangling link), and readlink, stat and
   lstat behave as they do on UNIX. Hard links are optional (may), but nlink must be maintained
   correctly either way.

Multi-user synchronisation and distributed file locking
The backend runs a lock manager that supports shared (read) and exclusive (write) locks. Locks are
leases: each has a time-to-live that the holder renews with heartbeats, so a crashed client cannot hold
a lock forever. Lock grants and releases are pushed over the WebSocket.

Writes also use optimistic concurrency. Every write carries the inode version it expects to replace. If
the version does not match, the write is a conflict. Conflicts are never resolved by silently overwriting
file content. The losing write is kept as a conflicted copy (report (conflict from student, 2026-11-14).md)
and the user is notified.

9.4 The window management subsystem
The compositor is the single authority over every window on screen. It keeps a window registry, a
hash map from window ID to window state:

   the owning process (pid), title and icon;
   position and size (x, y, w, h) and stacking order z;
   the window state (normal, minimised, maximised or full-screen) and the rectangle to restore to;
   whether the window has focus, plus its size limits.

The compositor is responsible for:

   Focus and z-order. Exactly one window has focus. Focusing a window raises it. Z-indices are
   renumbered 1…n after each change, so they never grow without limit. Background processes cannot
   steal focus.
   Coordinates and transforms. Dragging and resizing use pointer events with pointer capture.
   Movement is applied with compositor-friendly transforms (translate3d) and batched per
   animation frame, never by re-laying out the page on every event. The compositor supports resize
   handles on all eight edges and corners, keeps windows within the viewport, and snaps them to
   screen edges and halves.
   Minimise, maximise and restore, with animations that respect reduced-motion settings. Double-
   clicking a title bar maximises the window. Keyboard shortcuts are documented.
   The taskbar registry. The taskbar shows running applications grouped by app, marks background
   activity, and lets the user focus or minimise with a click.
   Window–process coupling. Closing a window sends a termination signal to its process, and killing
   a process closes its windows. Minimised windows are the first candidates for paging (§9.2), and
   restoring one triggers a page-in.

11.3 ACID guarantees for bulk operations
These operations must be atomic: recursive delete (rm -r), recursive copy (cp -r), directory moves
(especially to a new parent), batch renames (for example, 500 files renamed by the agent), recursive
chmod and chown, and the quota updates that go with all of them. Seven rules apply:

1. One transaction per user-visible operation. The whole subtree changes, or none of it does.
2. Quota checked inside the transaction. Lock the user's quota row (SELECT … FOR UPDATE or
    equivalent) so that two concurrent writes cannot both pass the check.
3. Invariants checked before commit. A directory cannot move into its own subtree (EINVAL). Names
    are unique within a directory, enforced by a unique index rather than application code.
4. Any error rolls back. The client receives one clear error code, and the database is exactly as it was
    before.
5. The client mirror is also atomic. The local change is one IndexedDB transaction across every
   affected object store. A half-applied local state is never committed.
6. Retries are safe. Idempotency keys make sure a retried operation is applied at most once.
7. The isolation level is declared and justified. For example: SERIALIZABLE with automatic retry on
   serialisation failure, or READ COMMITTED with explicit row locks. Explain why your choice is
   safe for tree operations.

11.4 Index optimisation
   A unique B-tree index on dentries(parent_ino, name). It serves every step of path resolution and
   every directory listing, and it enforces unique names. Mirror it on the client with a compound
   IndexedDB index on [parent, name].

   on blobs(sha256) for de-duplication.

   search, and optionally a trigram index for substring search.

12.4 Subsystem C: predictive process pre-fetching
A local machine-learning model analyses the user's telemetry to predict which applications they will
use next. It loads their assets into memory before they are opened, so that launch feels instant.

   Telemetry. Application launch, focus and close events, with time of day, day of week, the previous
   application and the position in the session. Events are stored locally in a bounded ring buffer. The
   user can view and clear them in Settings → Privacy. Nothing leaves the device without opt-in.
   Model. It must train and run locally, inside a worker. Acceptable choices include a first- or second-
   order Markov chain over launch sequences conditioned on time of day, naive Bayes, a small
   decision tree or logistic regression, k-nearest neighbours over context vectors, or a tiny neural
   network. Justify any model more complex than a Markov chain by showing that it beats one.
   Pre-fetch policy. When a prediction's confidence passes a threshold and the system is idle and
   there is free memory, the scheduler starts a pre-fetch process at the lowest priority. It loads the
   application's code, warms its caches and pages in its last state. Pre-fetched pages are marked
   speculative and are the first to be evicted.
   Learning. The model updates incrementally after each launch. Until it has enough data, it falls
   back to most-frequently-used.
   Evaluation. Replay a recorded trace of at least 500 launch events, split chronologically into
   training and test sets so the model cannot see the future. Report top-1 and top-3 accuracy against
   the most-frequently-used (MFU) and most-recently-used (MRU) baselines, launch latency with and
   without pre-fetch, and wasted pre-fetch bytes.

12.6 Models, cost and offline behaviour
   Choice of model. Hosted APIs or local models (on your backend, or in the browser through

14.1 Structure of STACK_DECISION.md
Write one decision record for each major decision, and keep them all in STACK_DECISION.md. Each
record contains:

1. Context and constraints. The WebOS constraints this decision affects, ranked. For example: main-
   thread responsiveness, offline operation, atomicity of tree operations, multi-user consistency,
    cost, team skills.
2. Options. At least three genuine candidates, including one you expected to lose.
3. Criteria and weights, declared before scoring. A weighted decision matrix whose criteria are not
   reverse-engineered from the winner.

14.3 What a strong justification looks like

  Weak (earns little or nothing)
  “We chose WebSockets because they are fast and modern, and we chose MongoDB because it is
  flexible and popular.”



  Strong (the standard expected)
  Process-state changes, lock grants and sync acknowledgements are initiated by the server, and arrive
  at up to about 20 per second per client during bulk operations.

  Polling every second would add up to a second of latency to every lock grant and cost about 3,600
  requests per hour per idle client. Long polling reduces the latency but still opens a new request for
  every event.

  A WebSocket gives one full-duplex connection with server push. Our prototype measured a median
  lock-grant latency of 38 ms, against 510 ms with one-second polling.

  Risk: some networks drop idle sockets. We mitigate this with 25-second heartbeats and resumable
  sessions using sequence numbers. We will revisit the decision if we need to support clients behind
  proxies that block WebSocket upgrades.

  The figures here are illustrative. Yours must come from your own measurements.


14.4 The defence session
The Phase 1 defence is 15 minutes of presentation and 10 minutes of questions. Every member
presents part of the architecture, and the examiners may ask any member about any decision. A
decision that only one member can explain is treated as undefended. If the defence is not accepted,
the team revises and re-presents within one week. The stack is then frozen; changing it later needs a
new decision record and the instructor's approval.

Section 18
Academic Integrity and the Use of AI Tools
   AI coding assistants are permitted, with disclosure. AI_USAGE.md records which tools were used,
   what they were asked, what was accepted, and what was rejected and why. The last part carries the
   most weight, because judging AI output is the skill being assessed.
   Everything you submit must be defensible in the viva. A member who cannot explain, justify or
   modify any part of their own submission when asked loses the marks for it, whether or not it
   works. Undisclosed AI use is an integrity violation.
   Study other systems; do not copy them. Studying Puter, daedalOS and other open-source systems
   is encouraged. Copying their code, or another team's code, is prohibited.
   Third-party code needs a licence and attribution. Any third-party code or library must have a
   compatible licence and be listed in THIRD_PARTY.md. It may never stand in for a mandatory DSA
   structure (§10.2).
   Secrets never go in the repository. API keys, database credentials and tokens do not belong in the
   repository or the client bundle. A leaked key must be revoked at once and reported in SECURITY.md.
   Contribution records must be authentic. Fabricated commit history, contributions attributed to
   the wrong person, or an agreement to “carry” a member who does not contribute are treated as
   misconduct under university policy.


  A final word
  Few student projects touch as many layers of computer science at once as this one. Build it as
  engineers: measure before you claim, defend every choice, and make the system tell the truth, from
  the first frame of the boot screen to the last line of the audit log.

  Give it a name you are proud of. It is your operating system.

Appendix B

Glossary
 Term                         Meaning in this project

 ACID                         Atomicity, Consistency, Isolation, Durability: the guarantees a transaction gives. Here,
                              above all, that a bulk operation happens completely or not at all.




Lahore Garrison University — Department of Computer Science                                                    Page 52 of 55
AI-Native Web-Based Operating System — Capstone Project Specification                                                Fall 2026


 Term                        Meaning in this project

 Aging                       Gradually raising the priority of a process the longer it waits, so that low-priority work
                             never starves.

 Blast radius                The set of files and inodes an operation will create, modify or delete, shown to the user
                             before an agent's plan runs.

 Cosine similarity           (a·b)/(‖a‖‖b‖), the cosine of the angle between two vectors; 1 means the same direction, 0
                             means unrelated.

 DAG                         Directed acyclic graph. Here, the graph of service dependencies whose topological order
                             is the boot order.

 Embedding                   A vector produced by a model to represent the meaning of a piece of text.

 Idempotency key             A unique ID attached to an operation so that retrying it never applies it twice.

 Inode                       The record describing a file, directory or link: type, owner, mode, size, times and where
                             its content is stored.

 Kahn's algorithm            A topological sort that repeatedly removes nodes with no remaining incoming edges. If
                             nodes remain at the end, the graph has a cycle.

 Lease                       A lock that expires unless renewed, so that a crashed client cannot hold a resource
                             forever.

 LRU                         Least Recently Used: the replacement policy that evicts the entry that has gone unused
                             the longest.

 OPFS                        Origin Private File System: a fast, private file-system storage area that the browser
                             provides to each origin.

 Outbox / operation          A durable queue of local changes, replayed to the server in order when connectivity
 log                         returns.

 p95                         The 95th percentile: 95% of measurements are at or below this value. Targets use p95 so
                             that averages cannot hide slow cases.

 Page fault                  An access to state that is not resident in memory, which makes the memory manager
                             page it in.

 PCB                         Process control block: the kernel's record for one process.

 Prompt injection            An attack in which text the model reads, such as a file's contents, contains instructions
                             meant to hijack its behaviour.

 Quantum                     The time slice a process may run before the scheduler reconsiders which process runs
                             next.

 RAG                         Retrieval-augmented generation: retrieve relevant documents first, then generate an
                             answer grounded in and citing them.

 Recall@5 / MRR              Retrieval metrics: the fraction of queries whose relevant file appears in the top five, and
                             the average of 1/rank of the first relevant result.

 Service Worker              A browser script that intercepts network requests, making offline operation and cached
                             shell updates possible.

 Topological sort            An ordering of a DAG's nodes in which every node comes after all of the nodes it depends
                             on.

 Trie                        A tree in which each edge is a character, so all words sharing a prefix share a path, which
                             makes prefix completion fast.

 Web Worker                  A background thread in the browser that runs JavaScript off the main (UI) thread and
                             talks to it by messages.
